## 1. 核心定位

### 1.1 我们做什么

本系统**不是**：

- 文本分析系统（只做情感/主题统计）
- LLM 预测系统（用自然语言“猜”未来）
- 暴力事件二分类预测器（“会不会出事？”）

本系统**是**：

> **文本证据编译器 + 运行时因果 Kernel + 逆向调试器**

在给定比赛、城市、媒体、线下人群和治理资源条件下，用**已知约束、历史机制先验和情景触发器**，推演不同风险路径与干预效果。

### 1.2 核心原则

| 原则 | 说明 |
|------|------|
| 不是预测未来数据 | 用机制先验 + 假设触发器做因果推演 |
| Atom 是证据，不是因果节点 | 只有 Compiled Event 能进入 Kernel |
| Observe many, compile once | 多次文本观察，只编译一次事件 |
| 机制是代码，因果是 metadata | `reads/writes/waits/resources/emits` 可审计 |
| 输出是路径，不是一句话 | 风险值 + 主导路径 + 阻断原因 + 干预差异 |

### 1.3 第一性原理

```
触发 → 检查 → 提交 → 传播 → 记录 → 干预比较
```

每一步都必须经过：flag 是否满足？资源是否够？优先级是否抢占？状态是否 commit？trace 是否记录因果来源？

## 2. 研究问题

### RQ1：比赛事件如何通过媒体框架和社交传播转化为线下风险？

研究比赛事件（争议判罚、出局、惨败等）如何沿机制链升级，而非预测单一终点。

### RQ2：哪些运行时条件会放大或阻断风险链条？

关注 flags、resources、priority、state 阈值等**运行时条件**，解释“为什么升级”和“为什么没发生”。

### RQ3：不同干预措施如何改变因果路径？

比较多世界（W0–Wn）下路径分叉、风险削减与最佳切断点（cut points）。

### RQ4：trace-first 因果引擎是否比普通 LLM 推演更可审计、更可解释？

从可追踪性、一致性、未发生事件解释、intervention diff、资源瓶颈定位五个维度对比。

## 3. 核心思想

### 3.1 整体数据流

```
原始文本 / 赛事情景 / 城市约束
        ↓
文本证据层：atom、去重、证据聚合（Phase 3）
        ↓
事件编译层：把证据编译成 typed event（Phase 3）
        ↓
运行时因果 Kernel：调度、条件、资源、状态提交（Phase 1）
        ↓
Trace Ledger：记录真实执行路径（Phase 1）
        ↓
Reverse Debugger：分析风险路径、瓶颈、干预效果（Phase 2）
```

### 3.2 关键分界

```
Atom          → 文本证据，不能直接 emit event，不能改 state
Claim Cluster → 证据聚合（support_count, velocity, confidence）
Compiled Event → 唯一能进入 Kernel 的 typed event
Mechanism     → 读/写 state，检查 flag，消耗资源，emit 下一事件
Trace Entry   → 记录因果来源、阻断原因、资源失败
```

## 7. 运行时因果 Kernel

### 7.1 时间模型（v0.1 约定）

- **调度方式**：事件驱动
- **时间戳**：离散整数（比赛分钟，0–120+）
- **同刻排序**：按 `priority` 升序（0 最高），同 priority 按入队顺序
- **delay**：相对当前事件时间的偏移，取机制先验区间中值或固定值

### 7.2 最小接口

```python
class Kernel:
    def emit(self, kind, payload=None, delay=0, priority=5, cause=None): ...
    def do(self, kind, payload=None, delay=0, priority=0): ...  # 干预注入
    def commit(self, event, patch): ...
    def set_flag(self, flag, cause): ...
    def clear_flag(self, flag, cause): ...
    def has_flags(self, *flags): ...
    def acquire(self, resource, amount, cause): ...
    def release(self, resource, amount, cause): ...
    def block_until(self, event, flags=None, resources=None, timeout=None): ...
    def run(self, until): ...
```

### 7.3 优先级

| Priority | 类型 |
|----------|------|
| 0 | 强制干预、紧急澄清、安全广播 |
| 1 | 争议判罚、冲突、恐慌、人群拥挤 |
| 2 | 媒体报道、谣言扩散、官方声明 |
| 3 | 球迷聚集、线下移动 |
| 4 | 普通 agent 行为 |
| 5 | 背景状态变化 |

### 7.4 资源失败语义（v0.1）

- 资源不足 → 事件**不执行**
- Trace 记录 `blocked_reason: resource_shortage`
- 不自动重试（便于解释瓶颈）

### 7.5 Flags 与 State 边界

- **State**：连续强度变量，机制 `reads/writes`
- **Flags**：离散因果门，机制 `waits`，由 commit 阈值或机制显式 `set_flag/clear_flag` 产生

## 8. 机制规范 Mechanism Spec

```python
@mechanism(
    kind="rumor_amplified",
    reads=["rumor_volume", "platform_velocity", "misinfo_confidence"],
    writes=["rumor_volume", "platform_velocity", "misinfo_confidence"],
    waits=["MEDIA_OUTRAGE_FRAME_ACTIVE"],
    resources=["media_attention_budget"],
    emits=["offline_mood_shift", "opposing_fans_contact"],
    version="v0.1"
)
def rumor_amplified(k, e):
    ...
```

### 8.1 必填 metadata 字段

| 字段 | 含义 |
|------|------|
| `kind` | 机制/事件类型 |
| `reads` | 读取的 state 变量 |
| `writes` | 写入的 state 变量 |
| `waits` | 前置 flags（全部满足才执行） |
| `resources` | 需要获取的资源 |
| `emits` | 可能发射的后续事件 |
| `version` | 机制版本 |

### 8.2 机制执行模板

```
1. 检查 waits（flags）
2. acquire resources
3. 读取 state + payload
4. 计算 patch
5. commit state + set/clear flags
6. emit 后续事件（带 cause 链）
7. 写入 trace
```

## 11. 逆向调试器 Reverse Debugger

### 11.1 核心函数

| 函数 | 用途 |
|------|------|
| `trace_path(event_id)` | 从事件反查因果链 |
| `why_blocked(event_id)` | 解释某事件为何未执行 |
| `why_not_happen(kind)` | 解释某类事件为何从未出现 |
| `resource_bottlenecks()` | 统计资源失败次数 |
| `flag_lifecycle(flag)` | flag 设置/清除时间线 |
| `variable_history(variable)` | 状态变量演化 |
| `dominant_risk_path()` | 风险主导路径 |
| `diff_trace(run_a, run_b)` | 两世界路径差异 |

### 11.2 示例输出

```
dominant path:
  controversial_call → media_blame_frame → rumor_amplified
  → opposing_fans_contact → verbal_conflict

why official_clarification failed:
  official_comm_channel required=1 available=0
  → RUMOR_SPIKE not cleared

diff_trace:
  Base:        controversial_call → media_blame_frame → rumor_spike → verbal_conflict
  Intervention: controversial_call → official_clarification → rumor_volume down → no rumor_spike
```

## 15. 风险与原则

### 15.1 主要风险

| 风险 | 缓解 |
|------|------|
| 机制参数来源被质疑 | 明确为敏感性区间 + 文献/专家依据表 |
| 机制数量膨胀 | 分阶段实现，先 A 链再 B/C |
| Flags 与 State 重复 | 严格分工，document 阈值映射 |
| LLM baseline 不公平 | 同场景 JSON、同输出维度比较 |
| 过度工程 | v0.1 坚持最小接口，不 premature abstraction |

### 15.2 开发原则

1. **先跑通，再完善**：一条链 + 两个干预 + 完整 trace
2. **机制是假设，不是真理**：每个机制带 version
3. **失败也要可解释**：blocked 事件必须进 trace
4. **实验可复现**：固定 seed、固定参数、输出 JSON artifact
5. **代码与论文同步**：每个 Phase 结束产出可引用图表
